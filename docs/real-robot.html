HiArm lower host

Set up and deploy on the real robot

This guide is derived from a read-only audit of the active HiArm source. It documents the observed contracts and safety gates; it does not claim that the robot was powered, calibrated, or moved during the audit.

14 follower jointsThree RGB camerasRobStride arm busesDamiao base/lift
01

Assign physical authority before powering anything

Qualified operator required.

One person must own the emergency stop or power disconnect. Another may operate the terminal. Both must agree on the planned joint set, duration, workspace, and stop signal before torque is enabled.

  1. Clear people, loose cables, tools, and objects from the swept volume.
  2. Support the arms if an unexpected torque release could cause impact.
  3. Place leader and follower near the recorded safe startup pose.
  4. Confirm the emergency stop or power disconnect is reachable without entering the workspace.
  5. Begin with software-only checks and progress one gate at a time.

Do not run motor scans, calibration capture, teleoperation, recording, or policy motion merely to “see what happens.” Several tools briefly enable torque to obtain feedback even when they are described as probes.

Two arm-control layouts exist in the source.

The generic HiArm robot class exposes one follower port plus chassis/lift. The current strict teleop, recorder, and policy client use separate left and right follower ports. Follow the active launcher used for the experiment; do not combine these port models.

03

Install the lower-host software without changing hardware state

Use the validated LeRobot/HiArm checkout supplied with the platform. The real-robot source is not copied into this KinRT package. Create an isolated environment and install the lower-host OpenPI client used to communicate with the GPU server.

Environment outline
cd /path/to/lerobot
python3 -m venv /opt/hiarm_env
/opt/hiarm_env/bin/pip install -e .
/opt/hiarm_env/bin/pip install -e /path/to/KinRT/policy/pi05/packages/openpi-client

cd src/lerobot/robots/hi_arm
OFFLINE_SELF_TEST=1 ./start_hiarm_pi05_policy_client.sh

Adapt the interpreter path in the launchers to the actual environment only in a reviewed deployment copy. The audited host used a dedicated hiarm_env and absolute paths.

Software-only gate

The expected output includes 14 motors, action shape (1, 14), and explicit statements that no cameras or serial/CAN devices were opened.

04

Discover stable device paths

USB topology changes can alter numeric device names. Prefer /dev/serial/by-path and /dev/v4l/by-id. Record the resolved mapping at the start of every collection or evaluation session.

Read-only discovery
ls -l /dev/serial/by-path
ls -l /dev/v4l/by-id
lsusb

# Confirm that expected paths exist without opening them.
test -e /dev/serial/by-path/<leader-device>

test -e /dev/serial/by-path/<right-follower-device>

The RobStride adapter uses an AT-style serial envelope, not SocketCAN or Lawicel/SLCAN. Do not attach a generic CAN tool to the device without confirming the transport.

05

Calibrate in a fail-closed sequence

The active strict path depends on leader calibration, follower rest/range calibration, and LeRobot-compatible direction/validation data. Treat calibration files as hardware-specific controlled artifacts.

ArtifactPurpose
leader_calibration.jsonLeader encoder and mapping reference
hiarm_rest_range_calibration.jsonFollower startup rest pose and safe absolute ranges
hiarm_lerobot_calibration.jsonDirection, homing/range compatibility, gains, and teleop validation
teleop_session_zero.jsonHistorical relative-zero compatibility; not the preferred primary map

Read current coverage

Calibration status
PYTHONPATH=/path/to/lerobot/src /opt/hiarm_env/bin/python \
  ./hiarm_rest_range_calibrate.py show

PYTHONPATH=/path/to/lerobot/src /opt/hiarm_env/bin/python \
  ./hiarm_lerobot_calibrate.py show

Validate one joint at a time

  1. Place leader and follower at the intended safe rest pose and record only the selected joint if a correction is required.
  2. Passively move that follower through a conservative safe range. Do not force a mechanical stop.
  3. Confirm direction with a tiny, supervised physical test.
  4. Mark the joint validated only after the direction and range are physically confirmed.
  5. Repeat until every selected joint has rest, range, direction, and teleop validation.
Do not use four named poses as proof of safety.

Whole-arm “middle,” “zero,” “rotation,” and “rest” snapshots do not prove per-joint direction, wrap continuity, or safe limits. The active safety path requires per-joint evidence.

Check orientation, exposure, focus, occlusion, left/right identity, frame freshness, and whether the physical setup matches training. A technically open camera with the wrong view is a failed gate.

07

Collect only after preflight passes

One bounded smoke episode
TASK="Put the pill box into the center of the notebook." \
REPO_ID="local/hiarm_smoke" ROOT="/data/hiarm_smoke" \
EPISODES=1 EPISODE_TIME=20 RESET_TIME=0 FPS=20 \
./start_hiarm_pi05_record.sh

The recorder connects separate follower buses, reads the leader, performs mandatory startup preflight, opens all cameras, clamps each target to calibrated ranges, limits per-frame motion, monitors fresh feedback, and disables follower torque in cleanup.

Record the command and output.

Keep the resolved ports, calibration digests, camera device IDs, task text, dataset root, preflight table, start time, operator, and stop reason with every collection session.

08

Deploy through offline, dry, and bounded gates

GATE AOffline self-test

No camera, serial, CAN, or motor access.

GATE BDry policy

Cameras and passive feedback; no motor commands.

GATE CBounded motion

Explicit motion flag and short duration.

GATE DBenchmark trials

Fixed protocol and physical supervision.

Gate A
OFFLINE_SELF_TEST=1 ./start_hiarm_pi05_policy_client.sh
Gate B
POLICY_SERVER="<gpu-host>:<port>" TASK_ID=0 \
  ./start_hiarm_pi05_policy_client.sh
Gate C
POLICY_SERVER="<gpu-host>:<port>" TASK_ID=0 \
  ALLOW_MOTION=1 DURATION=30 \
  ./start_hiarm_pi05_policy_client.sh

The audited launcher defaults to a 20 Hz loop, up to 20 actions from each returned chunk, a 60-second policy timeout override, explicit startup mismatch rejection, range clamps, joint-specific step caps, and stale-feedback termination. For first physical validation, reduce action-chunk execution to one step and use a short duration.

09

Stop immediately on any safety signal

SignalRequired response
Startup mismatch or failed calibration rowDo not enable motion; restore the pose or recalibrate the affected joint.
Unexpected direction, jerk, drift, or collision riskPress Ctrl-C and use the physical stop or power disconnect as needed.
Missing or stale follower feedbackStop, disable torque, inspect the relevant USB-CAN path and wiring.
Stale policy response or invalid action shapeStop the client; validate the server config and network before retrying.
Camera freeze, wrong view, or device contentionStop collection/evaluation and reacquire all three streams.
Limit sensor stale during lift useHold lift position and repair the limit-reader path before motion.

Normal cleanup disables follower torque and closes buses. A software cleanup path is not a substitute for a physical stop when the mechanism behaves unexpectedly.
